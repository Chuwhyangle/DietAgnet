# Diet Agent v0.5 扩展设计

> **目标**：让猫猫虫从“会调工具的 LLM”进化成“懂你的饮食教练”
> **核心方向**：主动 Agent + 动态计划建议 + 长期记忆 + 可审计知识/数据治理
> **状态**：部分落地
> **最后更新**：2026-05-13

---

## 总览

本期扩展把 Diet Agent 从单 Agent 工具调用模型，升级为具备**主动提醒、当天计划偏差判断、长期记忆、可审计数据治理**的进阶 Agent 应用。

当前项目已具备：

- 130 道中西式菜谱
- 饮食记录与每周统计
- AI 对话与 13 个本地工具
- AI 引导式计划生成
- 计划版本审计

v0.5 的重点不是继续堆功能，而是让已有能力串起来：用户制定计划后，系统能观察当天记录，发现偏差，并给出温和的补餐/减餐建议。

---

## 一、核心产品方向

### 1.1 会主动

猫猫虫需要从“用户问我才回答”升级为“在合适时机轻轻提醒”：

- 早餐/午餐/晚餐未记录提醒
- 用户记录一餐后的计划偏差检查
- 当天摄入过低或过高提醒
- 连续多天偏离计划提醒
- 每周复盘提醒

主动提醒必须低打扰，默认静音时段 23:00-07:00，同类提醒必须有冷却时间。

### 1.2 会动态建议

动态计划采用“建议调整”模式，不自动覆盖正式计划。

典型场景：

- 午餐计划 1000 kcal，实际记录 500 kcal：下午建议补充约 300-500 kcal，优先高蛋白、适量主食或轻加餐。
- 午餐超计划 400 kcal：晚餐建议降低油脂和主食，优先清淡蛋白和蔬菜，不建议惩罚性节食。

所有建议都需要用户确认，并写入审计记录。

### 1.3 会记忆

长期记忆用于记住用户偏好、过敏、忌口、作息和执行习惯。记忆用于提高建议质量，但用户必须能查看、删除或修正记忆。

### 1.4 会查证

RAG、embedding、食物成分表和膳食指南仍是后续方向，但不作为动态计划建议第一阶段的硬依赖。

原因：

- 当前 renderer bundle 已经偏大，继续引入 `@xenova/transformers` 和本地模型会显著增加体积。
- 动态计划第一阶段可以先基于现有计划、饮食记录、菜谱库和本地规则完成。
- 后续引入 RAG 时必须按需加载，不进入首屏关键路径。

## 三、主动 Agent 与动态计划

详细设计见 [proactive-agent-dynamic-plan-design.md](./proactive-agent-dynamic-plan-design.md)。

### 3.1 主动触发规则

| 规则 ID | 触发 | 条件 | 行为 |
|--------|------|------|------|
| `breakfast_check` | 定时 | 早餐未记录 | 提醒记录或推荐早餐 |
| `lunch_check` | 定时 | 午餐未记录 | 提醒记录午餐 |
| `dinner_check` | 定时 | 晚餐未记录 | 提醒补记晚餐 |
| `after_meal_plan_gap` | 记录变更后 | 餐次偏离计划 | 生成当天补餐/减餐建议 |
| `open_app_plan_drift` | 打开 App / 首页 | 最近多天偏离目标 | 提醒复盘 |
| `weekly_report` | 每周 | 本周记录天数 >= 3 | 提醒查看周报 |

### 3.2 动态建议原则

- 使用最新正式计划的热量目标；没有计划时退回设置页每日目标。
- 按餐次拆分当天热量目标。
- 单餐偏差超过 25% 且差值 >= 200 kcal 时，可触发建议。
- 摄入偏低时建议补充 300-500 kcal，不把全部缺口堆到晚餐。
- 摄入偏高时建议下一餐收敛，不建议不吃饭。
- 建议需要用户确认，不自动修改正式计划。

### 3.3 防骚扰机制

- 默认静音时段：23:00-07:00。
- 同类提醒至少冷却 4 小时。
- 用户连续 3 次忽略同一规则后，该规则自动降级或暂停。
- 用户当天选择“今天不提醒”后，同类规则当天不再触发。
- 浮层不能遮挡主流程按钮、抽屉或表单。

## 四、长期记忆系统

### 4.1 文件结构建议

```text
src/renderer/src/memory/
├── store.ts        # Dexie 读写封装
├── manager.ts      # 去重、合并、置信度更新
├── matcher.ts      # 关键词/标签匹配
└── prompt.ts       # 注入 system prompt 的格式化
```

### 4.2 核心 API

```typescript
export class MemoryManager {
  async remember(input: {
    type: Memory['type']
    content: string
    tags?: string[]
    source?: Memory['source']
  }): Promise<{ id: number; merged: boolean }>

  async recall(query: {
    types?: Memory['type'][]
    tags?: string[]
    limit?: number
  }): Promise<Memory[]>

  async forget(id: number, reason?: string): Promise<void>

  async buildMemoryContext(): Promise<string>
}
```

### 4.3 提取策略

- 用户明确表达偏好、过敏、忌口、作息或习惯时，Agent 可调用记忆工具。
- 对话后可以异步提取长期记忆，但 confidence < 0.6 的内容不入库。
- 设置页需要提供“我的偏好/记忆”管理入口，支持查看、编辑和删除。

## 五、菜谱数据治理

详细设计见 [recipe-data-governance.md](./recipe-data-governance.md)。

当前状态：

- 菜谱总数：120
- 原 `recipeExtensions.ts` 已超过 1500 行，当前已先拆为类型、中式菜谱、西式菜谱和统一出口；后续继续扩展时仍需保持这个结构
- 热量与宏量营养为估算数据

后续要求：

- LLM 估算只能生成校准候选，不能直接覆盖正式菜谱。
- 每条校准记录必须包含原值、新值、依据、置信度、风险备注、审核状态。
- 数据文件需要拆分为类型定义、中式基础、中式扩展、西式菜谱、校准补丁和校验脚本。
- 校验脚本必须检查重复 ID、缺失字段、异常热量、宏量偏差和分类统计。

## 九、风险与缓解

| 风险 | 缓解 |
|------|------|
| 主动提醒过于打扰 | 默认低频、静音时段、冷却、用户开关、忽略降级 |
| 动态建议误导用户 | 只做建议，不自动覆盖计划；极端场景给保守提示 |
| LLM 热量估算不准 | 只进入待审核，不直接覆盖正式数据 |
| 菜谱数据继续膨胀 | 先拆分数据文件，再扩充到 500+ |
| renderer bundle 继续变大 | RAG / embedding / 大知识库按需加载 |
| Dexie 迁移丢数据 | 在现有数据库上升级 schema，写迁移和备份策略 |
| 记忆系统记错事实 | confidence 阈值、用户可查看/删除/修正 |

## 十、扩展前后对比

| 维度 | v0.4（当前） | v0.5+（目标） |
|------|--------------|---------------|
| 菜谱数量 | 120 | 120，并进入可审计校准流程 |
| Agent 主动性 | 被动响应为主 | 定时 + 上下文触发 |
| 计划能力 | 静态计划版本 | 当天计划偏差建议 |
| 计划修改方式 | 用户重建计划 | 用户确认建议，不自动覆盖正式计划 |
| 记忆能力 | 当前对话与本地历史 | 跨会话长期记忆 |
| 数据治理 | 估算数据直接在代码中 | LLM 候选 + 审核 + 校验 + 回滚 |
| 知识来源 | 菜谱库 + LLM | 后续扩展为菜谱库 + 成分表 + 指南 |
| 性能策略 | 数据随 bundle 打包 | 大模型/知识库按需加载 |
