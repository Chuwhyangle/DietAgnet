# 主动 Agent 与动态计划建议 - 需求设计文档

> 最后更新: 2026-05-13
> 状态: 部分落地

## 1. 目标

把猫猫虫从“用户问才回答”的工具调用助手，升级为“能观察记录、判断偏差、主动建议”的饮食教练。

本阶段的核心不是自动接管用户计划，而是在用户当天实际摄入偏离计划时，给出温和、可执行、可审计的调整建议：

1. 用户没有按时记录餐次时，猫猫虫可以低打扰提醒。
2. 用户记录一餐后，系统检查当日计划与实际摄入差值。
3. 当实际摄入明显低于计划时，建议后续加餐或下一餐补足一部分。
4. 当实际摄入明显高于计划时，建议下一餐清淡收敛。
5. 所有建议都需要用户确认，不自动覆盖正式计划，不自动删除或修改用户饮食记录。

## 2. 核心原则

- **建议优先**：动态计划第一阶段只做建议调整，不自动改写长期正式计划。
- **用户可控**：每条提醒都可以关闭、忽略、稍后提醒或进入对话继续讨论。
- **低打扰**：默认静音时段 23:00-07:00 不提醒，同类提醒必须有冷却时间。
- **可审计**：每条提醒都记录触发原因、输入数据、建议内容、用户响应和时间。
- **保守健康建议**：涉及疾病、极端热量缺口、孕期/哺乳期、未成年人或 BMI 异常时，只给保守建议，并提示遵循医生建议。

## 3. 用户场景

### 3.1 未记录早餐提醒

用户早上 8 点以后还没有记录早餐。猫猫虫可以轻量提醒：

> 早饭还没记哦。吃过的话我可以帮你补一下；还没吃的话，也可以给你挑几个简单早餐。

用户可以选择：

- 去记录
- 推荐早餐
- 稍后提醒
- 今天不提醒

### 3.2 午餐摄入低于计划

用户当天计划午餐约 1000 kcal，但实际记录只有 500 kcal。

系统判断午餐摄入明显偏低后，下午提醒：

> 午餐比计划少了大约 500 kcal。下午可以补 300-500 kcal，优先选酸奶/鸡蛋/豆制品加一点主食，晚上就不用硬撑着补太多。

用户确认后，可以：

- 查看推荐加餐菜谱
- 跳转到饮食记录页
- 记录为“已采纳建议”
- 忽略本次建议

### 3.3 午餐摄入高于计划

用户当天计划午餐约 800 kcal，但实际记录 1200 kcal。

系统判断午餐超出计划后，提醒：

> 午餐比计划多了大约 400 kcal。晚餐可以清淡一点，优先选蛋白质和蔬菜，主食少量就好，不需要用不吃饭来补偿。

系统不得制造焦虑，不得建议极端节食。

### 3.4 长期偏离计划

用户连续多天热量明显偏离计划。

系统在打开 App 或进入首页时提醒：

> 最近几天和计划有点偏离，要不要一起复盘一下？我可以帮你看看是早餐、午餐还是晚餐最容易超出。

该场景不要求立即生成新正式计划，但可以引导用户重新制定计划或调整执行策略。

### 3.5 每周复盘提醒

如果用户本周至少记录 3 天数据，周日晚间或下次打开 App 时可以提醒：

> 本周饮食小结已经有足够数据了。要不要一起看看哪几天最稳、哪几餐最容易偏？

## 4. 触发规则

### 4.1 定时触发

| 规则 ID | 默认时间 | 条件 | 优先级 | 行为 |
|--------|----------|------|--------|------|
| `breakfast_check` | 08:00 | 今日早餐未记录 | low | 提醒记录或推荐早餐 |
| `lunch_check` | 13:30 | 今日午餐未记录 | low | 提醒记录午餐 |
| `dinner_check` | 20:30 | 今日晚餐未记录 | medium | 提醒补记晚餐 |
| `weekly_report` | 周日 20:00 | 本周记录天数 >= 3 | medium | 提醒查看周报 |

### 4.2 上下文触发

| 规则 ID | 触发时机 | 条件 | 行为 |
|--------|----------|------|------|
| `after_meal_plan_gap` | 新增/删除饮食记录后 | 当前餐次与计划差值明显 | 生成当天调整建议 |
| `open_app_plan_drift` | 打开 App / 回到首页 | 最近多天偏离目标 | 提醒复盘 |
| `overcalorie_streak` | 打开 App / 记录后 | 连续 3 天超过目标 | 建议查看原因和下一步策略 |
| `low_intake_warning` | 晚间或记录后 | 当天摄入明显低于目标 | 建议温和补充，不鼓励极端控卡 |

## 5. 动态计划建议规则

### 5.1 当日目标来源

第一阶段优先使用现有数据，不引入 RAG 或 embedding：

- 当前最新 `PersonalDietPlan.dailyCalorieTarget`
- 当前用户 `settings.calorieGoal`
- 当天 `DietLog` 汇总
- 餐次类型和已记录时间
- 用户档案中的 `mealsPerDay`、过敏/忌口、健康备注

如果没有正式计划，则退回 `settings.calorieGoal`。如果两者都没有，则不生成精确动态计划，只给记录提醒。

### 5.2 餐次目标拆分

需求层建议默认拆分：

| 餐次 | 三餐用户默认占比 | 四餐用户默认占比 |
|------|------------------|------------------|
| 早餐 | 25% | 20% |
| 午餐 | 40% | 35% |
| 晚餐 | 35% | 30% |
| 加餐 | 0% | 15% |

未来实现可以根据用户作息、训练时间、历史习惯调整比例，但必须记录依据。

### 5.3 偏差阈值

- 单餐低于计划 25% 以上，且差值 >= 200 kcal：可以建议后续补充。
- 单餐高于计划 25% 以上，且差值 >= 200 kcal：可以建议后续收敛。
- 当天总摄入低于日目标 30% 以上，且已到晚间：提醒适度补充。
- 当天总摄入高于日目标 10% 以上：提醒下一餐或明天回到节奏，不建议惩罚性节食。

### 5.4 补充建议

当摄入偏低时：

- 优先建议 300-500 kcal 的轻加餐或下一餐补足一部分。
- 优先选择蛋白质、适量主食和容易执行的食物。
- 不建议一次性把所有缺口堆到晚餐。
- 如果用户有过敏/忌口，推荐中必须避开。

### 5.5 收敛建议

当摄入偏高时：

- 优先建议下一餐减少油脂、甜品、重油主食。
- 不建议完全不吃下一餐。
- 不对用户做负面评价，不制造焦虑。
- 如果超额发生在午餐，晚餐建议清淡蛋白 + 蔬菜 + 少量主食。

## 6. 用户确认流程

Agent 提醒后，用户可以选择：

- `accept`：采纳建议，系统记录采纳状态，可跳转到记录页或推荐菜谱。
- `dismiss`：忽略本次建议，进入冷却。
- `snooze`：稍后提醒。
- `open_chat`：进入 AI 对话页继续讨论。
- `disable_rule`：关闭该类提醒。

系统不得在用户未确认时：

- 自动添加饮食记录。
- 自动删除饮食记录。
- 自动修改正式计划版本。
- 自动改变每日热量目标。

## 7. 数据模型

本节中的 `ProactiveEvent` 和 `DailyPlanAdjustment` 已完成第一阶段本地落地，均写入 Dexie 数据库 `diet-agent-planning`。

### 7.1 `ProactiveEvent`

记录主动提醒触发与用户响应。

```typescript
interface ProactiveEvent {
  id?: number
  ruleId: string
  trigger: 'cron' | 'context' | 'meal_log_update'
  priority: 'low' | 'medium' | 'high'
  firedAt: string
  delivered: boolean
  message: string
  userResponse?: 'accepted' | 'dismissed' | 'snoozed' | 'opened_chat' | 'disabled_rule'
  cooldownUntil?: string
  payload: Record<string, unknown>
}
```

### 7.2 `DailyPlanAdjustment`

记录当天动态建议。

```typescript
interface DailyPlanAdjustment {
  id?: number
  date: string
  sourcePlanId?: number
  ruleId: string
  mealType?: 'breakfast' | 'lunch' | 'dinner' | 'snack'
  plannedCalories: number
  actualCalories: number
  deltaCalories: number
  suggestedCalories: number
  suggestionType: 'supplement' | 'reduce' | 'maintain' | 'review'
  suggestionText: string
  recommendedMealWindow?: string
  userResponse?: 'accepted' | 'dismissed' | 'snoozed'
  generatedBy: 'local_rule' | 'agent'
  createdAt: string
  updatedAt: string
}
```

## 8. Agent 工具

计划调整、主动提醒历史查询与提醒偏好更新工具已完成第一阶段落地。

| 工具 | 用途 |
|------|------|
| `get_current_plan` | 已实现：读取当前正式饮食计划和热量/宏量目标 |
| `check_today_plan_gap` | 已实现：比较今日目标与实际摄入，返回剩余热量、餐次差值和偏差原因 |
| `suggest_plan_adjustment` | 已实现：根据当天偏差生成补餐/减餐建议 |
| `record_adjustment_response` | 已实现：记录用户对建议的采纳、忽略或稍后提醒 |
| `get_proactive_event_history` | 已实现：查询近期主动提醒历史，避免重复打扰 |
| `update_reminder_preferences` | 已实现：修改主动提醒开关、静音时段和冷却策略 |

## 9. 防打扰策略

- 默认静音时段：23:00-07:00。
- 同类提醒至少冷却 4 小时；高优先级健康风险提醒至少冷却 12 小时。
- 用户连续 3 次 dismiss 同一规则后，该规则自动降级或暂停。
- 用户当天选择“今天不提醒”后，同类规则当天不再触发。
- 模态框、抽屉、表单提交过程中的提醒不能遮挡主要操作，只能进入通知队列或浮层。

## 10. 审计点

每次主动提醒和动态建议必须记录：

- 触发规则 ID。
- 触发时间。
- 当时的正式计划目标。
- 当天实际摄入和餐次实际摄入。
- 计划差值。
- 生成的建议内容。
- 用户响应。
- 是否跳转记录页、是否打开对话页、是否采纳。
- 生成方式：本地规则或 Agent。
- 关联的计划版本 ID 和饮食记录日期。

## 11. 验收场景

| 场景 | 验收标准 |
|------|----------|
| 午餐计划 1000 kcal，实际记录 500 kcal | Agent 提醒下午可补 300-500 kcal，并推荐高蛋白/适量主食加餐 |
| 午餐超计划 400 kcal | Agent 建议晚餐降低油脂和主食，不自动删除或改写记录 |
| 用户未记录早餐 | 到设定时间后收到低优先级提醒，忽略后进入冷却 |
| 用户连续忽略同类提醒 | 规则自动降级或暂停，避免重复打扰 |
| 用户有过敏/忌口 | 补餐或推荐菜谱不得包含禁忌食材 |
| 晚间摄入明显过低 | 给出保守补充建议，不鼓励极端控卡 |
| 触发任意建议 | 可在审计记录中看到触发规则、输入数据、建议内容和用户响应 |

## 12. 当前不做

- 不自动生成新的长期正式计划版本。
- 不自动修改用户已经记录的餐食。
- 不把提醒推送到云端或移动端。
- 不引入 RAG / embedding 作为第一阶段必需能力。
- 不做医学诊断或疾病治疗建议。
