# Diet Agent - 产品需求文档 (PRD)

> 最后更新: 2026-05-13

## 1. 项目概述

**Diet Agent** 是一款桌面端个人饮食管理应用，帮助用户记录每日饮食、浏览菜谱、追踪营养摄入，并通过“猫猫虫” Agent 获得更主动、更连续的饮食陪伴。

项目当前已经完成本地优先的 MVP：菜谱浏览、饮食记录、营养统计、AI 对话、引导式专属计划、计划版本审计和首次使用引导。下一阶段的产品重点，是让 Agent 从“用户问才回答”升级为“能观察记录、判断偏差、主动建议”的饮食教练。

**人设**: 猫猫虫 🐛🐱 — 可爱、温暖、陪伴感、不过度打扰。

## 2. 目标用户

- 个人使用，不设置用户系统。
- 通过简单昵称进行个性化展示。
- 希望记录饮食、查看营养趋势，并获得可执行建议的桌面端用户。
- 不希望被复杂健康系统打扰，但愿意接受温和提醒和计划复盘的用户。

## 3. 核心功能

### 3.1 饮食记录

- 记录每日三餐（早餐/午餐/晚餐）及加餐。
- 手动选择或搜索食物/菜谱添加到记录中。
- 查看每日、每周饮食历史。
- 写入饮食记录后，后续阶段需要触发当天计划偏差检查，判断是否需要补餐、减餐或调整下一餐建议。

### 3.2 菜谱浏览

- 当前内置 **130 道中西式菜谱**，支持分类筛选、关键词搜索和详情查看。
- 菜谱内容包含：菜名、分类、食材、步骤、热量和宏量营养信息。
- 菜谱热量属于估算数据，后续必须建立可审计校准流程，避免错误数据长期影响计划与推荐。

### 3.3 营养追踪

- 基于饮食记录自动计算每日营养摄入（卡路里、蛋白质、碳水、脂肪）。
- 饮食记录页提供每周统计报表，展示 7 日摄入分布、完成度、目标命中日与本周洞察；**7 日列表附带宏量供能占比条（蛋白 / 碳水 / 脂肪）**，便于快速看本周结构。
- **已实现**：在饮食记录页展示「今日计划 vs 实际」面板——使用最新 AI 计划每日热量目标（若无计划则退回设置页每日目标），展示全天剩余热量、（实际 − 目标）差值，以及按餐次拆分的计划热量、实际记录与差值（计划 − 实际），与动态计划建议、Agent 工具使用同一套 `getDailyPlanGap` 口径。

### 3.4 个人设置

- 设置昵称。
- 设置每日营养目标。
- 配置 AI 对话通道和 API Key。
- 后续需要新增主动提醒相关设置：提醒总开关、静音时段、提醒类别开关、冷却策略展示。

### 3.5 AI 对话

- 用户可以与猫猫虫自然对话。
- Agent 通过 OpenAI Chat Completions 兼容接口调用模型，并通过工具读取或修改本地应用数据。
- 当前已支持查看营养、查询饮食记录、搜索菜谱、添加/删除饮食记录、更新设置、推荐菜谱和页面跳转；已支持计划差值、动态建议响应、主动提醒偏好、知识库检索与菜谱校准等扩展工具。
- 如果用户吃了菜谱库里没有的食物，Agent 可以根据名称、份量、品牌或做法做保守估算，并把结果保存为本地自定义食物，再写入当天饮食记录。
- **对话后异步记忆提炼**：在正式对话页每轮助手回复成功后，可异步调用模型从本轮对话抽取少量候选长期记忆（带置信度）；高置信度写入 `agent_inferred` 活跃记忆，较低置信度进入 **「待确认」** 状态，用户在设置页采纳或丢弃后生效。
- **用户节奏与习惯摘要**：基于本地饮食日志聚合过去 7~30 天（默认 14 天）的记录覆盖率、各餐次记录频率、工作日记录强弱与高频食物等，**自动注入 System Prompt**；并提供 `get_user_rhythm_summary` 工具供模型按需读取结构化结果。

### 3.6 AI 引导式专属计划

- 首页提供主线入口，启动逐步引导式资料采集。
- 逐项采集年龄、性别、身高、体重、目标体重、活动水平、餐次、饮食偏好、过敏/忌口、健康备注、做饭习惯和作息安排。
- 每一步即时写入本地数据库，支持后续审计。
- 输入异常或前后不一致时，追加追问补充说明。
- 资料收齐后生成并保存专属饮食计划。
- 当前计划是相对静态的版本结果；后续阶段需要增加“当天执行建议”，根据当日实际摄入偏差给出补餐/减餐提醒，但不自动覆盖正式长期计划。

### 3.7 主动 Agent 与动态计划建议

下一阶段的核心新增需求：

- Agent 可以在设定时间检查用户是否记录了早餐、午餐、晚餐或加餐。
- Agent 可以在用户记录饮食后，立即检查实际摄入是否偏离当天计划。
- 如果实际摄入低于计划，Agent 应给出补充建议，例如午餐计划 1000 kcal、实际吃 500 kcal，则下午建议补充约 300-500 kcal，优先推荐蛋白质、适量主食或轻加餐。
- 如果实际摄入高于计划，Agent 应给出下一餐收敛建议，例如晚餐降低油脂和主食、优先选择清淡蛋白和蔬菜。
- Agent 给出的是“建议调整”，需要用户确认；系统不得自动删除用户记录，也不得静默改写正式计划版本。
- 所有主动提醒和动态建议都必须写入审计记录，包含触发规则、当时目标、实际摄入、差值、建议内容、用户响应和时间戳。

### 3.8 菜谱热量校准与可审计数据治理

- 使用 LLM 对菜谱热量与宏量营养进行批量估算修正。
- LLM 输出不得直接覆盖正式菜谱数据，必须先进入待审核校准记录。
- 每条修正记录必须包含：菜谱 ID、原热量、新热量、蛋白质/碳水/脂肪、估算依据、置信度、风险备注、审核状态和更新时间。
- **审核通过后进入「应用内生效数据」**：以本地审计记录为真源，在读取菜谱库时合并**最新一条「已通过」**校准的估算热量与宏量；**Git 中的 TypeScript 菜谱源文件仍不自动改写**，便于审计与版本管理。将记录状态从「已通过」改为「已拒绝」或「需复核」等即可收回生效（回滚）。原始快照始终保留在校准记录中。
- 批量变更与发布流程仍应在 `docs/development-log.md` 等文档中留痕（人工流程）。
- 菜谱数据应从单一大文件逐步拆分为类型定义、基础中式菜谱、扩展中式菜谱、西式菜谱、校准记录和校验脚本，避免继续膨胀到难以维护。

### 3.9 文档同步与可审计要求

- 任何涉及功能、数据结构、Agent 工具、计划逻辑、菜谱数据、模型依赖或存储策略的变更，都必须同步更新 PRD、相关设计文档、开发日志和 README。
- 每个阶段必须记录目标、关键决策、影响范围、验证结果和未覆盖项。
- 文档中的“当前能力”和“后续规划”必须明确区分，避免把设计阶段能力误写成已完成。

## 4. 技术决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 平台 | 仅桌面端 | 当前需求只做桌面 |
| 数据存储 | 本地存储 (localStorage + Dexie) | 个人使用，无需后端；设置/日志继续走 localStorage，引导式计划、版本审计和后续主动事件走 Dexie |
| 用户系统 | 无，仅昵称 | 个人使用，简化设计 |
| AI 识别 | 暂不做 | 当前不做拍照识别食物 |
| Claude API | 暂不集成 | 目前优先兼容便宜的 OpenAI Chat Completions 风格接口 |
| 菜谱来源 | 开源菜谱 + 本地整理 + LLM 校准候选 | 先保障本地可用，再通过可审计流程修正热量 |
| 技术栈 | Electron + React + TypeScript | 生态成熟，开发快 |
| UI 风格 | Ant Design + 猫猫虫可爱主题 | 功能丰富 + 个性化萌系风格（已确认满意） |
| 动态计划 | 建议调整，不自动覆盖正式计划 | 降低误改风险，保留用户控制权 |
| RAG / embedding | 后续按需加载 | 避免 renderer bundle 和启动体积过快膨胀 |

## 5. 技术栈（已确认 ✅）

**Electron + React + TypeScript**

- **前端框架**: React 18 + TypeScript
- **桌面打包**: Electron 33 (electron-vite 2)
- **本地存储**: localStorage + Dexie（轻量直接；结构化计划与审计链使用 Dexie）
- **UI 组件**: Ant Design 5 + 自定义猫猫虫主题
- **构建工具**: Vite 5
- **路由**: React Router 6 (HashRouter)
- **日期处理**: Day.js
- **菜谱数据**: TypeScript 模块，当前内置 130 道菜谱
- **后续性能约束**: RAG、embedding、`@xenova/transformers` 和大体积知识库必须按需加载或异步初始化，不进入首屏关键路径

## 5.1 UI 设计风格 - 猫猫虫主题（已确认 ✅）

> 用户反馈：「还不错，就按照这个风格来做」

- **色调**: 柔和暖色系（奶油黄 `#FFF8E7`、柔粉 `#FFB6C1`、薄荷绿 `#B8E8D0`、薰衣草紫 `#E8D5F5`）
- **圆角**: 大圆角卡片 (12px~32px)，圆润可爱
- **字体**: Noto Sans SC，亲切温暖
- **装饰**: 猫猫虫 emoji 点缀 + 摇摆/弹跳动画
- **文案风格**: 俏皮、温暖（如「猫猫虫饿饿了」「吃好喝好，健康长大喵~」）
- **卡片**: 半透明毛玻璃背景 + 渐变色统计卡片
- **滚动条**: 粉色定制滚动条
- **背景**: 三色渐变（奶油黄→浅粉→薰衣草紫）
- **主动提醒 UI**: 后续提醒浮层必须轻量、可关闭、可稍后提醒，不遮挡主要操作。

## 6. 不做的事情 (Out of Scope)

- ❌ 用户注册/登录系统
- ❌ 云端同步/后端服务
- ⚠️ 拍照识别食物 — 有限范围：通过 OpenAI 兼容的视觉模型（如 Qwen-VL、GPT-4o）经由现有 chat-completions 代理实现食物照片估算。不引入原生 CV 管线、不捆绑离线图像模型、不持久化原始图片字节。
- ❌ 移动端/Web端
- ❌ 社交功能
- ❌ 自动进行医学诊断
- ❌ 未经用户确认自动改写正式饮食计划
- ❌ 未经审核用 LLM 估算结果覆盖正式菜谱数据

## 7. 菜谱数据方案

- 当前菜谱数据来自开源菜谱整理和本地扩展，已覆盖 130 道中西式菜谱。
- 菜谱统一整理为 TypeScript 模块，包含营养估算数据。
- 菜谱类型和数据已拆分为统一类型、基础/扩展中式菜谱、西式菜谱和统一出口，降低继续扩展时的维护风险。
- 热量和宏量营养需要进入可审计校准流程，先由 LLM 估算生成候选，再人工确认和落库。

### 7.2 菜谱治理要求

- 每个菜谱必须有唯一 ID、名称、分类、热量、宏量营养、食材和步骤。
- 每次热量修正必须保留原值和原因。
- 校验脚本需要检查重复 ID、缺失字段、异常热量、分类统计和宏量营养热量与总热量偏差。
- 大体量扩充前必须保持数据拆分和校验脚本有效，避免继续把大量数据堆入单个 TypeScript 文件。

**核心架构**：用户说话 → LLM API（带 Tool 定义）→ AI 返回工具调用 → 本地执行 → 结果回传 AI → 生成回复

**关键决策**：
- LLM API 选择便宜的（DeepSeek / 通义千问），支持 Tool Use。
- API 调用走 Electron 主进程 IPC 通道，安全隔离。

## 10. 测试体系

### 10.1 三层测试架构

项目采用三层模块分类，按模块职责决定测试深度和策略：

| 层级 | 覆盖范围 | 测试策略 |
|------|----------|----------|
| **Tier 1 — 纯逻辑** | `coaching/*.ts`、`coach/*.ts`、`data/recipeValidation.ts`、`export/dietLogExport.ts`、`habits/rhythmSummary.ts`、`knowledge/*.ts`、`memory/{matcher,manager,postChatExtraction,store}.ts`、`planning/*.ts`、`proactive/rules.ts`、`stores/*.ts` | 示例测试 + 属性测试（当存在可验证不变量时） |
| **Tier 2 — 集成胶水** | `agent/controller.ts`、`agent/tools.ts`、`agent/prompt.ts`、`main/agent.ts`、`main/dietLog.ts`、`main/index.ts`、`preload/index.ts` | 示例测试 + 结构化错误矩阵测试（依赖通过确定性 mock 注入） |
| **Tier 3 — 展示层 React** | `components/*.tsx`、`pages/*.tsx`、`App.tsx`、`proactive/ProactiveReminder.tsx` | 挂载冒烟测试：渲染不崩溃 + 至少一次用户交互验证 |

### 10.2 覆盖率目标

| 范围 | 行覆盖率 | 分支覆盖率 |
|------|----------|------------|
| 全局（`src/main/**`、`src/preload/**`、`src/renderer/src/**`） | ≥ 80% | ≥ 70% |
| `components/**` 和 `pages/**`（展示层） | ≥ 50% | ≥ 40% |

覆盖率由 `npm run test:coverage` 强制执行，未达标时命令以非零退出码终止，确保测试覆盖不会随代码增长而静默退化。

### 10.3 属性测试策略

对具有普遍不变量的行为使用 fast-check 属性测试（默认 `numRuns: 100`，CI 可通过环境变量提升至 500），覆盖以下 9 项正确性属性：

1. **解析器往返一致性** — `parse(serialize(x))` 在浮点精度 ±0.01 内结构等价
2. **静音时段遵守** — 提醒调度器在配置的静音时段内不产生任何触发事件
3. **过敏食材过滤** — 自动计划建议不包含用户标记为过敏/忌口的食材
4. **估算一致性** — 保存的饮食条目满足 `|蛋白质×4 + 碳水×4 + 脂肪×9 − 热量| ≤ 0.20 × 热量`
5. **计划不可变性** — 新计划提案不覆盖已接受计划的 ID，始终作为新行插入
6. **菜谱宏量营养验证** — 验证器对宏量供能与标注热量偏差超过容差的菜谱报告违规
7. **节奏摘要幂等性** — 对同一输入运行两次摘要产生相同结果；添加后移除一条记录等价于无操作
8. **记忆匹配器顺序无关性** — 打乱活跃记忆列表的输入顺序不改变匹配决策
9. **计划差值算术** — 对任意 `(目标, 实际条目)` 组合，`|剩余 + 实际 − 目标| ≤ 0.01`

### 10.4 测试隔离保证

为确保测试确定性和可重复性，测试套件强制以下隔离规则：

- **无真实网络** — 全局 `fetch` 守卫在未显式 mock 时抛出错误，任何测试不得发起真实网络请求
- **无真实时钟** — 依赖时间的测试通过 `vi.useFakeTimers()` 驱动，不依赖 `Date.now()` 实际值
- **无跨测试持久状态** — 每个测试前清空 `localStorage`，每个测试后删除 IndexedDB 数据库，恢复所有 mock
- **未刷新定时器检测** — 测试结束后若存在未清理的真实 `setTimeout`/`setInterval` 回调，测试自动失败

整个测试套件在典型开发机上 90 秒内完成，支持 `--shuffle` 模式运行以验证无顺序依赖。
