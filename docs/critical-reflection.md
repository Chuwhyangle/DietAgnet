# Diet Agent — Critical Reflection

> 本文档面向 Assignment 2 "Critical reflection"（10%）评分项。诚实记录项目的限制、失败模式、设计取舍与未来改进，而不是只展示成功部分。

## 1. Limitations（已知限制）

### 1.1 依赖远程 LLM

- **是什么**：Agent 的语义理解和工具决策由 OpenAI 兼容 API 完成（DeepSeek / 通义千问 / 自定义端点）。
- **代价**：
  - 没网就没 Agent。设置页有"测试连接"，但没有离线兜底。
  - API Key 一旦配错或额度耗尽，整个 Agent loop 就停摆。
  - 即使 API Key 由 `safeStorage` 加密，**对话内容本身**仍然会送到第三方模型——这对真正敏感的饮食/健康数据是个隐私边界。
- **当前缓解**：使用 DeepSeek/Qwen 这类便宜国产渠道降低额度焦虑；usage stats 持久化在主进程，用户可以看到 token 消耗。
- **未解决**：没有 local LLM fallback；用户没法选择"只发 SHA 哈希给云端"等隐私模式。

### 1.2 热量估算精度有限

- **是什么**：
  - 菜谱库的 130 道菜热量都是估算，不是逐道实测。
  - 库外食物（如 T2 山姆烤鸡腿）依赖 LLM 即时估算，偏差可达 ±30%（见 `evaluation.md` F1）。
- **代价**：用户长期相信"今天还剩 300 kcal"做晚餐选择，但实际可能已经超标 200 kcal。
- **当前缓解**：
  - 菜谱热量校准走 LLM → 待审核 → 人工审核 → 合并的可审计流程，不静默覆盖。
  - 一致性 invariant：`|蛋白×4 + 碳水×4 + 脂肪×9 − 热量| ≤ 20%`（property test 强制）。
  - 信任旋钮 `precision` 模式下每条估算需用户确认。
- **未解决**：
  - 没有食物条码/品牌库做硬约束。
  - 没有"分量识别"——用户说"一碗"，Agent 不知道是 200g 还是 400g。

### 1.3 本地优先、无云同步

- **是什么**：所有数据存在 `localStorage` + Dexie，**只在本机**。
- **代价**：
  - 换电脑就没了。
  - 没有手机端。
  - 主动提醒只在本机有效。
- **当前缓解**：导出脚本（`export/dietLogExport`）可以输出 CSV/JSON 做备份。
- **未解决**：没有云同步、没有 P2P 同步、没有移动端 companion app。

### 1.4 本地知识库是词法检索

- **是什么**：`knowledge/retriever.ts` 第一阶段使用关键词匹配 + 简单 reranker，没用 embedding 向量。
- **代价**：用户问"哪些食物消肿"找不到含"减少水钠潴留"的条目，因为关键词没对上。
- **当前缓解**：知识库内容人工挑选，覆盖最高频问题；`@xenova/transformers` 类大模型按需懒加载预案已留好。
- **未解决**：embedding 检索尚未启用，体感"知识库不够聪明"。

### 1.5 拍照识别能力有限

- **是什么**：所谓"拍照识别食物"是把图片交给视觉 LLM（如 Qwen-VL / GPT-4o）做估算。
- **代价**：
  - 没有原生 CV 管线，准确率受模型与拍照角度影响大。
  - 不持久化原始图片字节（隐私考虑），但代价是用户无法回看/校对。
- **当前缓解**：估算结果与计划差值一起展示，用户可即时手动修正份量。
- **未解决**：没有食物分割、份量重量估计、营养标签 OCR。

### 1.6 后台不是真后台

- **是什么**：应用最小化到托盘时主进程仍跑 30 分钟 tick；**完全退出后**就没人在听了。
- **代价**：用户彻底关掉 app，第二天打开才会看到积压的提醒。
- **当前缓解**：close 按钮默认改为"隐藏到托盘"，托盘里给"退出"明确路径。
- **未解决**：没有 Windows Service / macOS LaunchAgent / Linux systemd 单元。

### 1.7 不做医学诊断

- **是什么**：Agent 显式不做"你需要补铁"、"你血糖偏高"这类医学判断。
- **代价**：对真正有慢病的用户，Agent 只能"温和建议"而不能给精准方案。
- **当前缓解**：`dynamicPlan.ts` 的 `HEALTH_CAUTION_RE` 检测到"医嘱/糖尿病/孕期/未成年/进食障碍"等关键词时进入保守模式。
- **设计意图**：这是有意识的不做，**不是 bug**。

## 2. Failure Modes（已知失败模式）

### 2.1 模型不支持 tool_calls

- **触发**：自定义端点不实现 OpenAI tool 调用规范。
- **行为**：第一次请求触发 `AGENT_TOOL_REQUEST_FAIL` → 主进程缓存"此模型不支持工具" → 后续自动切纯聊天。
- **降级**：失去所有本地写能力（add_meal / remember / suggest_plan_adjustment...），等价于一个普通 chatbot。

### 2.2 Tool-call 死循环

- **触发**：LLM 反复要求同一组无解的工具调用。
- **行为**：`controller.ts:219-224` 通过 `buildToolCallSignature` 检测，抛"模型重复发起了同一组工具调用"错误。
- **代价**：用户看到错误而不是无限等待，但**本次对话失败**，没有自动恢复。

### 2.3 上下文截断

- **触发**：长会话超过 `MAX_HISTORY_MESSAGES = 20`。
- **行为**：早期消息被丢弃。
- **缓解**：长期记忆系统跨 session 持久化关键事实。
- **代价**：当前 session 内的临时上下文（如"刚才说我对牛奶不耐"如果还没触发 `remember`）会随之丢失。

### 2.4 用户输入歧义

- **触发**：用户说"我吃了一份意面"，但库里有"意大利肉酱面"、"白汁意面"、"番茄意面"三种。
- **行为**：当前 Agent 倾向于猜其中一种，而不是反问澄清。
- **代价**：可能记错菜谱 → 热量计算偏差。
- **缓解**：可在 prompt 中加强"歧义时反问"原则，但目前 prompt 偏向"先动手少废话"。

### 2.5 菜谱 miss

- **触发**：用户说出库外食物。
- **行为**：T2 描述的 `add_custom_food_meal` 链路，估算 + 保存。
- **代价**：F1 描述的估算偏差。

### 2.6 提醒重复 / 错过

- **触发**：用户在 tick 间隔（10/30 分钟）的"空窗期"内记录了餐次，下次 tick 才会看到，可能短暂出现"已经记了还在提醒"的边界情况。
- **缓解**：tick 内会再次 `getDietLog` 实时检查；每个 ruleId 有冷却时间避免轰炸。
- **代价**：在最差边界下可能弹一个"假提醒"，用户响应"我记过了"会立即关闭。

## 3. Design Trade-offs（设计取舍）

### 3.1 工具放渲染进程 vs 主进程

| 选项 | 优 | 劣 |
|---|---|---|
| 主进程（理想安全模型） | 隔离、好审计、跨进程统一 | 每次工具调用要序列化整个数据结构跨 IPC，性能与复杂度都涨 |
| **渲染进程（当前选择）** | 直接读写本地数据，零序列化开销 | 渲染进程相对没那么"硬"，但已通过把 API Key 留在主进程做隔离 |

**结论**：选了渲染进程。理由是数据本来就在渲染进程能直接访问，工具就近放最自然；高敏感的 API Key 隔离即可。

### 3.2 Express Onboarding（60 秒 5 字段）vs 完整 13 步问答

| 选项 | 优 | 劣 |
|---|---|---|
| 完整 13 步 | 数据全、计划个性化强 | 完成率低，新用户三天放弃 |
| **Express + 完整可选** | 60 秒拿到一个可用 plan | 初版 plan 精度弱于完整版 |

**结论**：默认 Express，完整版保留为"想精细化"的用户入口。这是教练 App 经典取舍。

### 3.3 Autopilot vs Precision（信任旋钮）

| 模式 | Agent 行为 | 适合 |
|---|---|---|
| **autopilot（默认）** | 高置信度估算自动落库 | 信任 Agent、追求低摩擦的用户 |
| precision | 每条估算都要用户确认 | 完美主义、对偏差敏感的用户 |

**结论**：默认 autopilot 因为"低摩擦"是教练 App 的核心价值；用户可随时一键切换。

### 3.4 主动提醒频率 vs 打扰感

| 选项 | 优 | 劣 |
|---|---|---|
| 高频（每 5 分钟） | 不会漏 | 烦 |
| 低频（每小时） | 不烦 | 容易漏 |
| **当前：前台 10 + 后台 30，叠加冷却、静音、连续忽略 3 次暂停 24h** | 自适应 | 实现复杂 |

**结论**：选了"自适应"。代价是 `reminderScheduler.ts` ~720 行，但被 `quietHours.property.test.ts` 等覆盖。

### 3.5 记忆置信度阈值

| 模型 | 行为 |
|---|---|
| 高 confidence 阈值（如 0.9） | 几乎不会误记，但很多有用信息漏掉 |
| 低 confidence 阈值（如 0.5） | 学得多，但可能误记错事 |
| **当前：双阈值 + pending_confirm** | 高阈值直入 active，低阈值进入"待确认"，用户决定 |

**结论**：让用户做最后裁判，Agent 不静默写入低置信度记忆。这一决策被 `memory/postChatExtraction.ts` 实现。

### 3.6 本地优先 vs 多端同步

| 选项 | 优 | 劣 |
|---|---|---|
| **当前：纯本地** | 隐私、无后端、启动快 | 换设备就丢 |
| 后端同步 | 多端、可云端备份 | 需账号系统、运维、隐私边界更复杂 |

**结论**：作业范围内坚持本地优先，未来扩展到 P2P / 自托管 sync 优先于"提供云端服务"。

### 3.7 一次性发 37 个工具 vs 按上下文挑选子集

| 选项 | 优 | 劣 |
|---|---|---|
| 全量发 | 简单 | 上下文膨胀，部分模型表现下降 |
| **provider-aware 子集选择** | 自定义渠道下按关键词激活工具组 | 实现稍复杂，规则可能漏匹配 |

**结论**：实现见 `controller.ts:117-144`。基础工具（查询/记录/菜谱）总是激活，planning / memory / knowledge / calibration 按关键词激活。DeepSeek / 通义千问 类成熟接口接受全量。

## 4. What Worked Well（哪些做对了）

1. **"Agent 不只是聊天"**：从 day 1 就把工具调用 + 主动行为放在第一位，避免做成普通 chatbot。
2. **本地优先**：数据在本机，没踩坑后端运维，作业可演示性更强。
3. **可审计**：所有写操作进入审计表，错了可回滚，方便 debug 和 demo。
4. **属性测试**：9 项不变量帮项目在持续重构中没崩；尤其 allergy 过滤、计划差值算术这两个被反复救场。
5. **进程边界清晰**：Main / Preload / Renderer 分得很干净，API Key 与业务逻辑明确隔离。
6. **Express Onboarding 这个产品决策**：把"60 秒拿到一个可用 plan"放在首页主线，对新用户的演示效果远好于 13 步问答。

## 5. What Didn't Go As Planned（哪些没达预期）

1. **OS 通知体验**：Windows 通知中心样式受 Action Center 折叠规则影响，长文案被截断；曾尝试自定义浮层，发现 Electron 在 Win11 上嵌入 Toast XML 太脆弱。
2. **Embedding 知识库**：原计划接 `@xenova/transformers` 做语义检索，发现首次加载 ~50 MB 模型会显著拖慢 dev 启动；改为"按需懒加载"占位，但当前未实际启用。
3. **完整 13 步问答完成率**：早期数据显示 < 30% 用户能走完，因此把 Express 提升为默认。
4. **拍照识别**：第一版尝试做原生 CV pipeline，发现工程量过大，转为"借用视觉 LLM"——这是一个有意识的范围收缩。
5. **多模型 A/B**：原计划做"同 prompt 在 DeepSeek vs Qwen vs OpenAI 上的成功率"自动报告，目前只完成了人工抽样。

## 6. Future Improvements

按优先级排序：

### 短期（1~2 周）

- [ ] **多模型对比脚本**：自动跑 `evaluation.md` T1–T8 在 N 个 provider 上的 tool-call 成功率与延迟，输出 markdown 报告。
- [ ] **Agent 反问机制**：在 prompt 加入"歧义时先反问"原则，缓解 §2.4 失败模式。
- [ ] **OS 通知样式优化**：Win11 Toast XML 改用 `@nodert-win10-rs4` 系列 native 接口。
- [ ] **菜谱 LLM 批量校准脚本**：当前是 Agent 工具触发的，按需执行；目标是夜间一次性跑校准 + 自动写待审。

### 中期（1~2 月）

- [ ] **Embedding 知识库**：启用 `knowledge/embedder.ts`，按需懒加载，**只在首次调用 `search_knowledgebase` 时初始化**。
- [ ] **Conversation Summarization**：每 20 轮做一次本地 summarization，缓解上下文截断（§2.3）。
- [ ] **食物分量识别**：用户说"一碗"时弹出"小碗 200g / 中碗 300g / 大碗 400g"快速选择。
- [ ] **真后台**：Windows Service / macOS LaunchAgent 形态，应用退出后也能跑 tick。

### 长期（≥3 月）

- [ ] **跨设备同步**：先做手动导入导出，再考虑端到端加密的 P2P 或自托管 sync。
- [ ] **移动端 companion**：先做"只看不写"的 React Native / Tauri Mobile 端。
- [ ] **可穿戴接入**：HealthKit / Google Fit 读取活动量，反向校正每日 kcal 目标。
- [ ] **食物条码扫描**：作为 LLM 估算的硬约束兜底。
- [ ] **Local LLM fallback**：用 llama.cpp / Ollama 在本机跑小模型做基础工具决策，云端模型只在复杂任务被调用。
- [ ] **用户研究**：找 5~10 个真实用户用 4 周，做"主动提醒采纳率 / 长期记忆准确率"的实证研究。

## 7. Key Takeaways for the Course

如果让我给"build an intelligent software agent"再做一次，会保留这些选择：

1. **从一开始就投资工具系统**：早期把 7 个核心工具做对，比后期补 30 个工具有用得多。
2. **把"可审计"当一等公民**：动态计划、记忆、校准全部写审计表，让 demo 时能"打开 DevTools 看证据"。
3. **属性测试是 agent 项目的安全网**：常规单元测试盖不住"打乱顺序后过敏过滤还成立吗"这类 invariant，但 fast-check 很自然。
4. **不追求一次做完所有 agent 能力**：goal / memory / planning / proactive 四个核心拿稳，比"也做 RAG 也做 CV 也做语音"更稳妥。
5. **本地优先省事**：作业范围里没必要为云同步消耗工程量。
